# Rule evaluation

What every built-in rule finds, measured over five asset folders, and what was decided about each
rule as a result.

`samples/` carries deliberate defects, listed row by row in `samples/expected-findings.tsv`.
`corpus/` carries none: every file in it is written to demonstrate the correct, defensive practice
for one family of rules, so a finding there is a false positive by construction. `samples-field/`
carries field-style code — auto-loan batch and CICS programs in a production house style — with
its seeded defects in `samples-field/expected-findings.tsv` and every other finding accepted with a
reason in `samples-field/baseline.tsv`. All three folders are synthetic, hand-written for this
repository with nothing copied from a real system; the field folder is the one whose idioms
(catalogued PROC, `IKJEFT01`, DCLGEN, `WHENEVER`, `HANDLE CONDITION`, SORT procedures, `ALTER`,
`COPY REPLACING` with pseudo-text) come from what production shops write.

`corpus-public/` (public course material, CC-BY-4.0) and `corpus-constructs/` (hand-written
fixtures, one per JCL and SQL construct family) were added for the JCL and SQL coverage work;
their accepted rows live in their own `baseline.tsv`. Neither is defect-free the way `corpus/` is.
corpus-public is third-party teaching material and carries real defects; a corpus-constructs
fixture written to carry a construct — `RESTART=` on a JOB card, a step that allocates none of its
program's DDs — satisfies the rule that reads it. A row in either file is therefore a true finding
on such a fixture or a rule limit, and its own reason says which.

`RuleEvaluationReportTest` produces the table below. It runs `lint` over the five folders with
every rule forced on, ignoring any `rules.json`, so a rule that ships disabled is still measured.
Every finding on a folder that carries a baseline, other than a seeded defect, must be listed in
that folder's `baseline.tsv` with a written reason; the test fails on a finding that is not, and
on a baseline row that no longer fires, so noise arrives as a diff someone has to read.

## Verdicts from the field measurement (2026-09)

The field folder carries 38 defects: 37 seeded, plus a dead EXIT paragraph (D38) that the rule
work itself surfaced. 37 of them a rule could report (D33 is a call-graph fact); the rules report
34 of those, at 35 sites, and draw three accepted false positives. Precision on the field folder
is therefore 35 / 38 over all rules, and 1.0 for every rule except R005 (1 / 4).
R008, off by default, adds 90 findings when the harness forces it on; they are accepted wholesale,
as in the corpus, and are not in that count.

## Verdicts from the JCL and SQL rules (2026-09)

Ten rules, R050 to R059, for what a job's JCL says and what an embedded SQL statement does.
`samples/` gained three files to carry them — `jcl/SYKD040.jcl`, `cobol/SYK010.cbl` and
`cobol/SYK011.cbl` — with one seeded defect per check, rows 21 to 36 of
`samples/expected-findings.tsv`. The rules were measured over the three folders of the table below
and over `corpus-public/` and `corpus-constructs/`, the two folders added for the coverage work,
whose accepted rows live in their own `baseline.tsv`. Four rules were narrowed against what the
measurement drew (R052, R055, R056, R057), and R058 ships off.

| rule | verdict | the number that decided it |
|---|---|---|
| R050 undefined reference in JCL | **new** | 4 / 4 on samples: an undefined symbol, an override naming a step the PROC does not have, a referback to a step the job does not define, and a PROC member no library holds. The first three are ERROR, the JCL being wrong; the missing member and an unexpanded PROC call are NOTE, marking the edge of what was analysed rather than a defect. An override or a referback written under a call whose member was never read is left alone: that member may hold what it names. A symbol matches on a word boundary, so `&MODE` does not land on the step that carries `&MODEL`. 0 on corpus and samples-field |
| R051 duplicate DD name in one step | **new** | 1 / 1 (`SYKD040` STEP010 writes SYSOUT twice). Only the first statement of a concatenation counts as a definition, so the nameless statements under a DD draw nothing. 0 on corpus and samples-field |
| R052 DD of a SELECT the step does not allocate | **new, narrowed** | 1 / 1 on samples; 2 accepted on the field folder, both the skeletal FLJ030 step that runs FLB010 with a SYSOUT DD and nothing else. A file the program never opens is skipped, which cleared FLB010's SORTWK: it is an SD the COBOL SORT serves through SORTWKnn, and no step has reason to carry a DD of that name. 0 corpus |
| R053 operator parameter left on the JOB card | **new, MEDIUM** | 1 / 1 on samples (`RESTART=STEP020`), reported at the JOB card the job model carries; 1 accepted on the field folder (FLJ020 restarts from the last run's cut-off on purpose). MEDIUM rather than HIGH: the job runs and does less than the member describes, rather than failing |
| R054 UPDATE or DELETE with no WHERE | **new** | 1 / 1 on samples. A positioned update (`WHERE CURRENT OF`) draws nothing. Declares SQL as well as COBOL, so a script's unqualified UPDATE is reported too. 0 on corpus and samples-field |
| R055 cursor used out of order | **new, narrowed twice** | 5 / 5 on samples, one per defect kind, and 0 elsewhere only after two narrowings. This CFG keeps a PERFORM node's sequential-successor edge beside its call edge, so a walk from the entry steps over every PERFORM body: the walk for a skipped OPEN was narrowed to the paragraph holding the use (it had reported the CLOSE and the FETCH of trailing error paragraphs across the corpus folders), and a second OPEN has to be a second statement (the same OPEN reached again, which a re-entered paragraph produces, had drawn one finding per such paragraph). `ALLOCATE CURSOR` counts as an OPEN (CSQ305:92), `EXEC CICS SYNCPOINT` ends the unit of work of a CICS program, and a ROLLBACK is walked only for a cursor an OPEN of it reaches |

A WHERE clause, an aggregate anywhere in a select-list entry and any FETCH FIRST clause exempt the statement, and so does reading `SYSIBM.SYSDUMMY1`, which holds one row by definition — that exemption cleared four findings on CSQ408. 0 on corpus and samples-field |
| R057 column outside the table's declaration | **new, narrowed** | 1 / 1 on samples. The declaration is matched on the schema as well as the table (CSQDB.JUCHU is not FLDB.JUCHU, which cleared CSQ102:40); a column of a WITH clause, and every unqualified column of a statement that has a WITH clause at all, is skipped, because a common table expression has no declaration to be measured against; so are a name the select list defines with `AS` and the format keyword of a built-in (`CHAR(x, ISO)`). A CREATE TABLE in a DDL script is read as a declaration, though a finding in a script is not reported. 0 on corpus and samples-field |
| R058 schema-qualified table | **new, default off** | 16 samples findings, 14 on the field folder and 4 on the corpus, none of them a defect: all three folders spell every table `SCHEMA.TABLE`. Whether to qualify is a site convention, so the rule ships off and is accepted wholesale in the corpus and field baselines. It reads a degraded statement too, a keyword scan recovering the table names |
| R059 INSERT with no column list | **new, NOTE** | 1 / 1 on samples. An INSERT naming its columns, and one whose source is a SELECT that names them, draw nothing. NOTE: the statement works until a column is added to the table |
